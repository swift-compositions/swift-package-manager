# swift-package-manager

Use this package when a tool needs to ask SwiftPM about a package on disk, or to rewrite the dependency clauses in a `Package.swift`. Start from `Package.Manager` to evaluate a manifest, read the resolved workspace state, find where a dependency's sources were checked out, put a dependency in edit mode, or build a product. After a build, `Package.Build.Plan` holds the commands that build ran, and `Package.Build.Plan.replay(changed:product:timeout:)` rebuilds a change to a target's source files by running those commands for that target and the product's link, without SwiftPM; when it refuses, run the ordinary build. Use `Package.Manifest.Redirection` to point a URL dependency at a local path and back, and `Package.Manifest.Identity.Conflict` to find one package identity declared at two locations. The value types these return come from swift-spm-standard, which this package re-exports. For a dependency graph across many packages in a workspace, use swift-package-graph.

## Laws

- `Package.Manager` runs SwiftPM as a subprocess on every call, with nothing cached. With the default `Package.Manager.launcher`, `swift` is found through `/usr/bin/env`, or `cmd.exe` on Windows. Any other `executable` is run directly as the `swift` binary.
- Each subprocess has a timeout, 120 seconds by default. A subprocess that ends by a signal is reported as timed out, whatever sent the signal. For `Package.Manager.edit(_:path:at:timeout:)` and `Package.Manager.unedit(_:at:force:timeout:)` it is reported as locked instead when SwiftPM's stderr says another instance holds the build directory. Any other unsuccessful exit keeps SwiftPM's stderr.
- With `scratch` set, SwiftPM keeps its state there and leaves the package's `.build` alone. `Package.Manager.resolution(at:scratch:)` only reads `workspace-state.json` from that directory, or from `.build`, and never runs SwiftPM.
- `Package.Manager.manifest(at:timeout:scratch:)` keeps only the name, tools version and dependencies, with no products on the dependencies. A source-control dependency takes its first remote URL. Use `Package.Manager.evaluation(at:timeout:scratch:)` for the full manifest.
- `Package.Manager.catalog(at:timeout:scratch:)` reads `Package.swift` before and after evaluating it and fails if the bytes changed. It records SHA-256 hex digests of those bytes and of the output of `swift --version`. Version-specific manifests such as `Package@swift-6.3.swift` are not part of the digest.
- `Package.Manager.Materialized.source(of:at:scratch:)` gives a managed checkout's path under `checkouts` in the scratch or `.build` directory, never its declared location. A file-system or edited dependency gives its recorded path.
- `Package.Manifest.Clause.all(in:)` finds each `.package` followed by optional whitespace and a balanced argument list. Parentheses inside string literals don't count. Unbalanced parentheses end the search without an error. Comments are not skipped. `Package.Manifest.Dependency.SourceControl.all(in:document:)` blanks comments first, and so does `Package.Manifest.Source.code(in:)`, which keeps every byte offset and line break.
- A package's identity is the last path component of its URL, with trailing slashes and `.git` removed, lowercased.
- `Package.Manifest.Redirection.redirect(_:dependency:to:)` finds the first clause whose URL has the same identity, not the same text, and replaces it with a path clause whose backslashes and quotes are escaped. `Package.Manifest.Redirection.restore(_:planned:declared:)` needs that exact path clause in the source. A redirect followed by a restore gives back the original bytes.
- `Package.Manifest.Identity.Conflict` compares locations after trimming, lowercasing, dropping the scheme, turning `git@host:path` into `host/path`, and removing trailing slashes and `.git`. An identity with more than one location is a finding. It is fatal when manifests declare two or more of the locations, and a stale pin otherwise. Findings are sorted by identity, and their entries by location and then document.
- `Package.Manifest.Identity.Conflict.entries(inResolved:document:)` returns no entries when the text isn't valid JSON, without an error.
- `Package.Manifest.Identity.Conflict.isRootManifest(_:)` accepts `Package.swift` and `Package@swift-` followed by digits and dots and `.swift`.
- `Package.Manager.build(product:at:scratch:timeout:configuration:)` runs `swift build -c <configuration> --product <product>`, with a 30-minute timeout by default. A failing build keeps both of SwiftPM's streams, because compiler diagnostics come on stdout.
- `Package.Build.Plan(product:at:scratch:configuration:)` reads the task stores Swift Build, SwiftPM's default build system, leaves under `out/Intermediates.noindex/XCBuildData` in the scratch directory, which defaults to `.build`. Each build request has its own store. The plan comes from the store the build used last among those holding a link step whose output is `Products/<Configuration>/<product>`: Swift Build appends a store's signature to `prior-build-descriptions.txt` each time it builds from it and does not write the store again, so the last line naming a store decides, and the stores' modification times only order those the file does not name. The choice matters because two requests' compile commands may differ in an argument the compiler writes into the module file, such as whether diagnostics are coloured, and a replay with the other store's command would then always refuse as `interface`. The store's format is Swift Build's own, not a published one: a store this package cannot read gives no plan.
- A plan holds compile steps by module name, link steps by output path, and signing steps by the path they sign. A compile step runs in the directory its `-working-directory` names, and every other step in the package directory.
- `Package.Build.Plan.replay(changed:product:timeout:)` never runs SwiftPM. It refuses as `unlisted` when a changed path is in no compile step's source file list, so a new file, the manifest or a resource needs the ordinary build. A changed path matches a listed one as the list writes it, after its quotes and escapes are removed, or else with symbolic links resolved on both sides, so `/var` and `/private/var` name the same file. It refuses as `unlinked` when no link step makes the product, before it compiles anything.
- For each module a changed path belongs to, the replay compiles the module and compares the bytes of its `-emit-module-path` file before and after. Other targets read a target only through that file, so identical bytes mean nothing downstream is stale; any difference refuses as `interface`. A compile that exits unsuccessfully is a `compile` error with the module and both of the compiler's streams, since the ordinary build would fail the same way. Then it runs the module's merge, the link step whose file list lies beside the module's output file map, then the product's link and its signing, if the store has one.
- A refusal after a compile has run leaves newer objects than the last build, and the ordinary build rebuilds them from the changed sources.
